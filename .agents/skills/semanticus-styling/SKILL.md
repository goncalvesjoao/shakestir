# Semanticus Styling

Make Semanticus and custom CSS share a common visual foundation for spacing, font sizes, radii, and responsive thresholds. The goal is a coherent product: related areas should feel designed together, even when their layouts and visual treatments differ.

Creative custom CSS, new components, expressive typography, and distinctive layouts are welcome. Use Semanticus as a starting point and shared vocabulary, not a ceiling on design. Extend or adjust the shared system when it helps the product; do not flatten deliberate hierarchy or distinctive treatments just to reduce custom CSS. Prefer reuse for repeated, ordinary decisions and make intentional differences part of the design language. Success is visual coherence and usable behavior, not the fewest custom classes, literal values, or exceptions.

Preserve the user's visual intent, behavior, accessibility, and explicit design choices. Approximation and utility composition are useful options, not requirements to force every design into an existing component.

## Discover the real API

Read the project's theme, stylesheet load order, relevant templates/components, and installed Semanticus CSS or source. Identify its version and any project conventions. Verify candidate classes, variables, component slots, typography defaults, and responsive breakpoints against that build. Use official documentation when local evidence is insufficient. Do not invent utilities or rely on an API from a newer release.

Inspect the effective cascade before deciding what a rule does. Check later declarations, shorthand/longhand interactions, inherited variables, media queries, and all places the component is rendered. An earlier `margin-bottom` may already be reset by a more specific rule. Remove superseded or unused rules instead of applying utilities that revive their obsolete values. Account for classes generated by helpers and JavaScript before declaring a selector unused.

## Complete utility-pruning requests systematically

When the user asks to prune custom CSS or replace it with Semanticus utilities, audit every rule and declaration in the requested scope. For an application-wide request, cover all application stylesheets and their rendering contexts; for a component request, keep the audit local. Token normalization and a few obvious substitutions do not complete a utility-pruning request.

1. **Build a version-matched utility inventory.** Read or extract the installed build's utilities, including responsive variants. Cover display, flex/grid layout, alignment, wrapping, spacing/resets, sizing, positioning, typography, borders/radii, overflow, and image fitting. Record selectors, declarations, `!important`, media conditions, and inherited custom-property effects as needed to evaluate candidates. Search the actual declarations as well as class names; names alone do not establish equivalence. Keep this inventory in working notes or an existing project audit rather than copying a full framework catalog into this skill. Recheck any cached reference against the installed version and application theme.
2. **Inspect each custom declaration.** Determine whether it is unused/superseded, already supplied by the element or framework component, expressible by verified utilities, or genuinely custom. Inspect matching templates, shared partials, helpers and JavaScript-generated markup, including conditional classes and every context in which the selector applies. Audit mixed rules property by property; a custom color or dimension does not justify retaining unrelated utility-covered layout declarations.
3. **Implement suitable replacements.** Apply the verified component/modifier/utility composition to all relevant rendering paths and remove the corresponding CSS declarations. Remove empty rules and obsolete media blocks. Delete unused or superseded declarations directly instead of reproducing them with utilities. Reuse existing hooks for state and behavior where needed.
4. **Justify retained candidates.** For declarations with a plausible utility equivalent, identify the concrete reason to retain them: unavailable API, a required value or relationship, conditional/shared-context behavior, or an observed cascade/state/responsive conflict. Existing placement in a custom class, a general preference for custom CSS, or the mere possibility of a conflict is not sufficient. Investigate the conflict; retain CSS when evidence supports it. Group repeated reasons by component or pattern rather than documenting every harmless declaration.
5. **Re-audit the remainder.** Search the remaining CSS against the inventory after migration, inspect missed matches, and verify the affected rendering paths and states. A textual match is a candidate, not proof that replacement is safe.

Completion means every rule in scope has been reviewed, suitable replacements have been implemented, and remaining utility-covered candidates have concrete retention reasons. Report coverage, representative migrations, meaningful exceptions and verification limits. If a rendering context or stylesheet could not be checked, name it and describe the remaining work rather than claiming the pruning is complete. Do not broaden a local request, force unsuitable utilities, or redesign the interface merely to reduce declaration counts.

## Choose the smallest useful composition

Prefer, in order:

1. The correct native HTML element and an existing Semanticus component or modifier that already does most of the job.
2. That component plus a custom class that configures verified public component variables and adds only the product-specific differences.
3. A new product-specific class composed with Semanticus utilities in the markup, keeping only the properties utilities cannot suitably express in custom CSS.

These are decision preferences, not a compulsory class hierarchy. A component plus a couple of utilities may need no custom CSS at all. Keep useful custom classes as state, behavior, or styling hooks without duplicating framework properties in them.

“Extend” means composing classes on the same element and customizing supported variables; ordinary CSS does not inherit declarations from another class. Do not introduce a preprocessor, `@extend`, `@apply`, duplicate utility definitions, or a parallel component system just to imitate this composition.

Preserve semantics when choosing a visually close component. Use links for navigation and buttons for actions. Do not add a button role or menu/tab behavior merely to obtain its appearance.

## Align margins, padding, gaps, and radius

For ordinary whitespace, compare the desired distance with nearby **actual** Semanticus values. Prefer a close native step when it preserves grouping, hierarchy, readable density, and usable hit targets. Avoid a new token for every small difference such as 12px versus 8px or 16px.

- Use existing `--spacing-*` values in custom CSS where a utility is unsuitable. Prefer utilities directly when they express the element's invariant spacing.
- For site-wide scale changes, consider configuring Semanticus through its public theme variables so components and utilities agree. Check affected forms, navigation, dialogs, cards, and viewport widths. A local refinement does not justify changing the entire scale.
- Keep vendored CSS unchanged by default; place configuration in the application theme after the framework. Edit upstream or vendor code only when that is part of the requested scope.
- Treat radii by role: actions, fields, cards, and overlays need not share one radius. Prefer the nearest existing modifier or radius token, or configure the appropriate public slot. For example, verify whether the installed version separates `--buttons-border-radius` from general `--border-radius` and card/input slots. A generic `rounded` utility may use a different token than a component.
- Do not round typography, border thickness, shadows, artwork sizes, or column proportions merely because spacing is being normalized.

Do not assume token suffixes count pixels or base units. For example, **in a theme with `--spacing: 1rem` and the corresponding five-step Semanticus scale**, utility suffixes 1–5 may resolve to 4, 8, 16, 24, and 48px. Verify this mapping; `gap-3` is then 16px, not 12px. Do not assume a spacing token and a similarly numbered radius utility share a scale.

### Precise exceptions are legitimate

Keep a named custom token when approximation would damage an approved composition, sticky-header clearance, artwork overlap, or another real constraint. Centralize it, derive it from the shared scale where appropriate, and record its value and purpose. Preserve existing exception names when the project uses them to track possible Semanticus additions.

For example, **if `--spacing-1` is 4px**, `--space-36: calc(var(--spacing-1) * 36)` makes an intentional 144px distance visible and searchable. Prefer that tracked exception over repeating `calc(var(--spacing-3) * 9)` across unrelated selectors. Do not eliminate custom tokens simply to claim exclusive framework usage. Conversely, do not hide every ordinary intermediate distance behind a new `calc()` expression.

Keep actual relationships as relationships: an action aligned with an avatar can use avatar width plus its gap. Splitting a gap into child margin and parent padding is useful only when both sides serve the layout. Check margin collapse, backgrounds, borders, clickable bounds, and responsive wrapping; do not manufacture wrappers or redistribute spacing merely to reproduce an arbitrary number.

## Align font sizes and typographic roles

Review the actual Semanticus font-size defaults, heading and control variables,
size modifiers, available text utilities, and the project's typography settings.
Identify repeated roles such as page title, section heading, body, label,
metadata, and action text. Related roles across pages should share a coherent
scale; each component should not independently invent a near-identical size.

- Prefer a nearby existing font-size token, semantic default, size modifier or
  utility when it conveys the intended role and preserves readability and
  hierarchy. Inspect what a modifier changes: a control size class may also
  change padding and line height.
- When the product needs a different typographic scale, configure Semanticus's
  verified public typography variables and apply that scale to custom styles
  too. Update shared role tokens or documentation where the project has them.
  Avoid changing a global base size merely to fix one label or screen.
- Custom display sizes, fluid `clamp()` treatments, typefaces, and intentional
  exceptions are welcome. Relate their endpoints or hierarchy to the shared
  scale where useful. Reuse a named role when a new treatment recurs; a
  one-off expressive treatment need not become a universal token.
- Keep heading levels and other HTML semantics based on document structure.
  Use styling to obtain the desired appearance rather than choosing the wrong
  heading level or component purely for its font size.
- Treat font size, weight, line height, measure, and tracking together. Body
  and metadata must remain readable; visual consistency does not require
  identical typography for every role or forcing type onto the spacing grid.

Check rendered text with realistic content, long names and translations when
relevant, browser zoom or enlarged text, and narrow layouts. Look for clipping,
unexpected wrapping, compressed controls, and loss of hierarchy. Explain
intentional new type roles or scale changes instead of silently adding a
separate font-size system in one area.

## Share a breakpoint system

Treat breakpoints as part of the design system, alongside spacing, typography and radius.
The aim is for Semanticus components, responsive utilities, and custom CSS to
change together where they describe the same layout transition.

Inspect the installed framework's actual breakpoint definitions and the
application's media queries, responsive class suffixes, and related JavaScript
or image-sizing conditions when relevant. Map repeated custom thresholds to
nearby native thresholds before introducing another one. Verify units and
boundary behavior; do not silently equate rem/em thresholds with fixed pixel
values using an assumed root font size.

Choose according to the layout evidence:

- **Prefer the current Semanticus thresholds** when a nearby breakpoint keeps
  the layout readable, prevents overflow and premature wrapping, and preserves
  usable controls. Use native responsive utilities or the same thresholds in
  custom CSS. Consolidate near-duplicate application queries for the same
  transition rather than keeping a slightly different cutoff in each component.
- **Adjust Semanticus's breakpoint configuration** when the product needs a
  different shared responsive system. Inspect the supported source/build
  configuration first; update the common definitions and regenerate the
  framework output reproducibly, including affected responsive utilities and
  component queries. Update corresponding application queries and relevant
  behavior conditions so the framework and application actually agree. A
  custom threshold with the old framework utilities still in place is not a
  shared system. Broad breakpoint changes must fit the requested scope and
  be checked across affected components.
- **Retain a documented exception** when a component genuinely fails at the
  nearest shared threshold and changing the entire framework would be
  disproportionate. Record the threshold, the layout constraint, and why the
  native choices do not work. Keep exceptions deliberate and reviewable.

Do not assume Semanticus exposes runtime breakpoint variables. Ordinary CSS
custom properties cannot parameterize `@media` conditions: defining
`--breakpoint-md` does not make `@media (min-width: var(--breakpoint-md))`
work or retarget compiled `.gap-md-*` classes. Use the project's existing
build-time breakpoint mechanism when available. If no configurable build is
available, prefer the installed thresholds or a recorded exception; describe
what source/build work a framework-wide change would require. Avoid adding a
new toolchain solely to centralize a few media-query literals, or hand-editing
scattered generated queries as an undocumented customization.

Match inclusive/exclusive boundaries consistently. Test just below, at, and
just above every changed threshold, plus representative widths between them.
Check the transition itself: navigation wrapping, grid columns, field/control
widths, image containment and visibility must remain coordinated. Report
intentional threshold changes and update the project's breakpoint documentation
or shared configuration when it has one.

## Move properties into utilities without breaking the cascade

Check the installed utilities for layout, alignment, wrapping, borders, spacing, resets, and image fitting before writing those declarations again. Prefer small combinations such as:

```html
<div class="d-flex gap-4 border-top pt-2 recipe-actions">…</div>
```

When these classes match the intended behavior, remove the redundant `display`, `gap`, `border-top`, and `padding-top` declarations from `.recipe-actions`. Keep any genuine component-specific styling. A border utility is equivalent only when its width, style, and color match, including contrast states.

For conditional styling in a shared partial, pass or use the existing component context to apply the utility only where needed. Do not apply a personal-library reset to every public recipe card.

Utilities commonly use `!important`. Before replacing a property, inspect:

- **Breakpoints:** follow the shared-breakpoint decisions above. `gap-3 gap-md-4` must use the same verified `md` threshold as related custom layout rules. Do not defeat a responsive utility with a competing near-duplicate media query.
- **States and print:** display utilities must not defeat `[hidden]`, closed dialogs, mobile-only hiding, or print rules. Padding and border utilities must not suppress selected, error, focus, or higher-contrast treatments.
- **Contextual spacing:** avoid broad `m-0` or `p-0` when only one side needs resetting. Consider the framework's own form/search-group behavior and contextual indentation.
- **Inherited tokens:** color and component utilities may change custom properties inherited by descendants, not just one computed property. Avoid collateral changes.

If a utility would require another `!important` override to restore the intended behavior, leaving the property in component CSS is usually clearer.

## Verify and report

For a small change, inspect the affected element and its important states. For broad refactors, compare representative catalogs, details, forms, dialogs, and shared partial contexts at desktop, tablet, and phone widths. Test around any changed breakpoint. Include print, reduced motion, or contrast when the affected rules involve them.

Compare related areas for a shared visual rhythm, typographic hierarchy, radius treatment, and responsive behavior. Use computed styles and element geometry to distinguish intentional scale changes from regressions. Look at the rendered result as well: equivalent dimensions do not establish equivalent color, radius, focus behavior, or clipping. Run relevant existing checks; do not require a full-site audit for a trivial utility substitution.

Report what moved to Semanticus, what remains custom and why, any intentional visual or breakpoint changes, and what was verified. When the project maintains a design-system document or exception register, update the relevant entries rather than creating duplicate documentation. Stay within the requested styling scope.
